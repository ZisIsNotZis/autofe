# 页面构图与意图校验（composition）

状态：当前事实（就地重写，不带历史叙事）。
溯源：构图层缺口由 10 页视觉诊断确认（证据：`.scratch/63-recapture-recuration/design-diagnosis.md`）；本文件是该层的唯一事实家，诊断记录只作证据不作事实源。

本层回答一个问题：**页面级「怎么排」由谁定、如何保证引擎真的做到了。** 它位于「业务语义（模型）」与「DOM/CSS」之间。

## 1. 语义归属 vs 形态：谁声明、谁决定

- **页面语义归属（scope/subject）是闭式业务事实，必须由模型声明**。它回答「这是站点入口、某一分类、一次查询、一个实体、一份文档、还是账号/表单」以及「主体是商品/dataset/文档/账号」。
  - 证据：仅凭业务结构推导，10 类里只能干净分出 5 类，40 页最好 20/40 与 19 页残留；`landing/home` 与 `category/list` 同构（12 页，同站成对）、`product-detail` 与 `article/editorial`/`table-heavy` 同构。这不是阈值问题，是缺一个语义位（`.scratch/63-recapture-recuration/composition-derivation-analysis.md`）。
  - 它是**闭式枚举**（如 `_composite`），不是 UI 旋钮、不是逐页手写样式；由采集/策展依据源站页面角色自动填入。
- **布局框架与媒体角色是引擎的形态决策**：同一 scope/subject 可以由引擎选不同的 band/网格/阅读列；模型不表达这些。
- 因此本层既改引擎（构图推导与框架），也向语法加**两个闭式语义键**；不加任何表现/样式键。
- 反例：在模型里写 `_kind: "catalog"` 或每页 CSS，是表现混入语义或站点级逃生口，仍禁止。

## 1.1 两个闭式语义键

| 键 | 闭式取值 | 含义 |
|---|---|---|
| `_scope` | `entry` / `category` / `query` / `entity` / `document` / `account` / `form` | 页面在站点中的角色 |
| `_subject` | `offer` / `document` / `account` / `dataset`（可缺省） | 页面的主体种类 |

采集 archetype → 语义键的映射（迁移依据）：

| 采集 archetype | `_scope` | `_subject` |
|---|---|---|
| `landing/home` | `entry` | — |
| `category/list` | `category` | — |
| `search-results` | `query` | — |
| `product-detail` | `entity` | `offer` |
| `article/editorial` | `document` | `document` |
| `docs/design-system` | `document` | `document` |
| `profile/account` | `account` | `account` |
| `table-heavy/admin` | `entity` | `dataset` |
| `dashboard/data-viz` | `entity` | `dataset` |
| `form/checkout/settings` | `form` | — |


## 2. 构图必须完备，不得静默回落

- 每个页面解析出恰好一个页面原型（闭式集合：`reading` / `catalog` / `marketing` / `detail` / `product` / `authentication` / `search` / `profile` / `table`），否则是**显式错误**。（`feed` 不是独立原型：它是 §3 里 catalog / feed / search 共用的框架族，今日语料 0 页需要单独原型。）
- `default` 不是合法结果。解析不出原型 = 引擎错误（门禁失败），不是「普通页」；门禁在渲染上要求页面带上与其原型对应的页级类（`reading-page` / `<kind>-page`）。
- **覆盖口径诚实**：40/40 是「声明 → 投影」检查，不是「从结构推导出原型」——40 页都声明了 `_scope`/`_subject`，因此测度分支在真实语料上 0 次触发；结构规则与含混负样本由自测行使（`composition-selftest.mjs`）。声明的**正确性**是策展事实，门禁只能保证声明不被静默改写。
- **唯一实现**是 `m1/axis.mjs` 的 `pageLayoutOf`（返回 `kind` 与裁定它的 `rule`，裁不出时 `kind` 是 `undefined`）；门禁 `m1/eval/composition-selftest.mjs` 在 pipeline 里运行，断言 40 页各自落在其采集 archetype 的允许集内，并用含混负样本证明树会诚实返回 `undefined`。
- 判定依赖业务结构（角色、`_lines`/`_items` 层级、`_rel`、关系、复合件）加两个闭式语义键（scope/subject）；**不得**依赖站点名或逐页例外。声明与偶然计数不可互换：声明了 scope/subject 的页面由声明裁定，计数（长段数、价格数、横幅数）只在未声明角色的页面上兜底——否则 4 个商品页会被长段数判成阅读页。
- 长文/阅读型判定统计**全部长文本**（`_text`、`_quote`、`_summary`、`_detail`，嵌套含 `_lines`），不得只看单一字段。

## 3. 布局框架（frames）是一等概念

页面原型映射到真实框架，而不是把一切倒进同一个文档列：

| 原型 | 框架 |
|---|---|
| marketing / landing | band 序列（满幅或色带）+ 居中/交替排版 |
| reading | 居中阅读列（单一 measure，hero 收敛到该列） |
| catalog / feed / search | 卡片网格 / 记录行网格；feed 用「主列 + 侧栏」两区（判定见下条：只在 catalog 原型上，`search` 保持结果行） |
| detail | 媒体墙 + 主列 + 任务卡（右侧或栏内停靠） |
| profile | 居中身份卡 + 统计块 + 活动 feed |
| authentication | 居中表单卡 |

- **区域（region）**：主列与侧栏是两个区域，侧栏内容不得在单列流里掉到正文之后。
- **feed + 侧栏（两区帧）**：页面主体是**一个占优的集合**（成员数 ≥8 且 ≥ 次大集合的 2 倍）时，排在它**之后**的**短卡片小节**（单张卡片，或成员 ≤6 的短集合）进右栏（380px，滚动停靠），feed 占左主列；排在它之前的小节（视图切换、创作入口）留在主列、feed 之上。判定全属引擎侧（`m1/axis.mjs` 的 `feedRailOf`，规则名 `feed-and-side-cards`，模型不新增键）：同站没有站点名、没有逐页例外。两个反例保持单列（自测负样本）：并列集合（两个 feed 而非 feed+侧栏）、以及本来就有自己帧的原型（`search` 的结果行、`marketing` 的 band 序列不重切成两区）。链接列（纯目的地列表）与长文小节不是侧卡，留在主列、跟在两区之后，不因帧判定被吞掉。**覆盖口径诚实**：40 页里只有 `sspai-com/matrix` 触发（1/40），其余 39 页的单列形态不变。
- **入口矩阵的列数整除入口数**：营销页 ≥4 个带目标控件的矩阵按入口个数取列（6→3 列、8→4 列，素数走均衡拆分 7→4+3），不留 4+2 的偏行；判定是 `m1/axis.mjs` 的 `matrixColumns`，落成容器上的 `--matrix-cols`。窄视口降为 2 列 / 1 列。
- 区域按声明角色取宽；页级框架决定对齐基线，局部表单不得各自选宽（沿用 `docs/m1/layout-axes.md` §5.2「容器按内容收缩」）。
- **记录行按自身量宽封顶**：一行 = 文字列（`--measure-row`）+ 媒体槽（216px）+ 声明间距（24px），整行 `max-width` 取这三段之和；拉得比这更宽，未用的中段就是文字与图之间的空白。媒体留在源站那一侧（feed 右、搜索结果左）。
- **瀑布流（waterfall）**：成员高度无法等高的卡片集合用 column 流（`break-inside:avoid`），不用行网格——行网格把短成员垫进空洞、让最长者给整行定行距。判据在 `render.mjs` 的 `masonryOf`，全属引擎侧、模型不新增键：① 成员文字量差距过大；② 营销页的图片卡片墙（页框没有给卡片媒体声明比例框，高度由原图比例决定）。候选容器仅是页框真会排成多列行网格的集合（轴层声明的列数，或 catalog 页框自己的多列网格）。统一网格（catalog 卡片的媒体框声明为 4/3）保持行网格。
- **入口矩阵**：营销页一页里 ≥4 个**带目标**的控件是一张入口矩阵（每个入口一张卡），不是一排药丸；动作栏（无目标 / 不足 4 项）形状不变。营销页一个小节的短列表（标题 + 一行事实）是 2–3 列卡片格。
- `[开放]` 「局部最优」布局研究（`docs/design-basis.md` §6）若落地，必须在构建期/缓存完成，运行期只套用方案。

## 4. 媒体角色（media roles）

- 图片按**声明的角色**定尺寸：hero/band 充满其框架；卡片缩略图充满其格子；正文插图受阅读列约束。
- 不得只按原图像素绘制（`width:auto`）而留下白洞或小图。
- 保持「绝不放大源图」判据（`docs/m1/layout-axes.md` §7.1）：按角色布局的是**容器**，图像在容器内等比、不放大。

## 5. 意图校验门禁：声明 → 兑现 → 大声失败

引擎必须把意图说成机器可读的声明（每页原型、每区框架、每媒体角色），渲染后校验计算样式是否兑现；不兑现即错误。三类检查：

1. **未定构图**（`default`）→ **错误（阻断）**。
2. **死选择器**（引擎 CSS 引用的结构类在冻结语料上 0 次打出）→ **警告（不阻断）**。语料不必行使每个引擎能力；把「未被语料行使」当阻断会逼人删掉合法能力。页面原型**已解析却未打出对应类**属于错误（由第 1 项覆盖），与此不同。
3. **死声明**（同一元素上永远不可能生效的重复声明）→ **错误（阻断）**：作者写出了自相矛盾的意图。
4. **运行时意图未兑现**（声明意图的实际计算样式被覆盖 / 在窄视口失效 / 学科缺失）→ **错误（阻断）**。这是自动化版的 DevTools 划线删除；须报出「声明值 / 实际值 / 获胜规则」。

- 阻断项是**线上正确性**（构图未定、意图未兑现、声明自相矛盾）；死代码只作警告，可见但不逼删能力。
- **可证伪**：门禁必须先用已知缺陷做负样本证明能抓到，再谈通过（`docs/proof` 的 gate_probe 原则）。
- 权重口径：与既有「门禁全绿只是必要条件」一致；本门禁只证明「引擎兑现了自己的声明」，不证明设计好看——后者仍靠人审与独立复核（`docs/product.md` §2）。

## 6. 剩余缺陷（框架 / 设计层，S2 / S3）

- 侧栏是**结构推出**的两区帧，不是语义声明：`_region` 裁决仍缺，所以站点导航被捕获成根节点（`navigation`）而不是 `header` 区域时，它只能留在主列（`sspai-com/matrix`）。
- 卡片的媒体高度在渲染期不可知（模型不带原图尺寸），所以「高度参差」只能用内容量或页框性质作代理判据；代理由此做出的 waterfall 不保证逐页都是最优列数。
- `search` / `table` / `profile` 原型仍只有通用形态，未到原型专属框架。
- 媒体尺寸角色只覆盖声明过的 hero/banner 与卡片格；正文插图只有阅读列约束。
- 排版仍是单一 system-ui、2× 标题层级、中文 74ch 行宽（S3）。
- 潜在残留：`.linklist.cols{2,3,4}` 的 `column-gap` 被合并规则的 `gap` 简写覆盖（属性键不同，门禁不报；删除为视觉零变）。

## 7. 验收（10 页样板，铺开前）

- 10 个缺陷页作为样板：每页原型非 `default`、声明意图 100% 兑现、门禁负样本全部被抓。
- 交付形态：每页「原站 | 渲染」并排图 + 门禁报告。
- 样板通过后才铺到全部 40 页并重跑全部门禁 + 新独立验收。

## 8. 开放缺口（已知、暂不掩盖）

- **dashboard/data-viz 无语法表达**：语料里唯一的 dashboard 页 `num 0`、无图表/序列/带单位的值原语；它现在只能落到 `table` 原型（框架未实现，S2）。需要一次图表原语的语法演化（n=1，先在结果里记录限制，不假装已解决）。
- **框架缺口**：`search` / `table` / `profile` 原型尚无 CSS 框架（11/40 页带着无效果的页级类），由 S2 落地；门禁只查「CSS → 语料」方向，不查「页级类 → 有框架」。
- **`docs/design-system` 与 `article/editorial` 同属 document**：两者共用阅读框架；`docs/design-system` 在语料里 n=1，暂不单独建模。
- **`table-heavy` 的表「角色」靠位置近似**（深度 1 的表=页级数据集，实体下的表=属性面板）；这是策展纪律，不是不变式。
- **两处建模缺口（不是推导规则问题）**：`sspai-com/login` 缺 `login` 声明（推导按 `_scope:form` 判定）；`mi-com/search-phone` 缺查询态。
- **`search.results` 绑定只有 6 个搜索页中的 2 个声明**（huawei 两页带 `_default` 查询态），其余 4 页靠 `_scope:query` 判定；结构无法自证它们是结果页，故结构规则只认声明的绑定，不退回 facet 代理。
