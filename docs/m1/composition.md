# 页面构图与意图校验（composition）

状态：当前事实（就地重写，不带历史叙事）。
溯源：构图层缺口由 10 页视觉诊断确认（证据：`.scratch/63-recapture-recuration/design-diagnosis.md`）；本文件是该层的唯一事实家，诊断记录只作证据不作事实源。

本层回答一个问题：**页面级「怎么排」由谁定、如何保证引擎真的做到了。** 它位于「业务语义（模型）」与「DOM/CSS」之间。

## 1. 构图是引擎的形态决策，不是模型原语

- 模型只表达业务：角色事实（`_title`/`_image`/`_price`/`_text`/`_quote`…）、关系（`_lines`/`_items`/`_rel`）、动作（`_action`）、意图（`_intent`）、复合件（`_composite`）。
- 页面原型（品类页 / 文章 / 落地页 / feed / 搜索 / 个人页…）、区域带（band）、侧栏（aside）、媒体角色都是**形态**，由引擎决定。因此本层只改引擎，不改模型语法、不加 UI 键。
- 反例：把「这是商品列表页」写进模型 = 表现混入语义，等价于站点级逃生口，违反 `docs/design-basis.md` §5。
- 模型保持纯业务 ⇒ 「无站点级 CSS/表现逃生口」的验收判据不破（`docs/product.md` §2）。

## 2. 构图必须完备，不得静默回落

- 每个页面解析出恰好一个页面原型（闭式集合：`reading` / `catalog` / `marketing` / `detail` / `product` / `authentication` / `feed` / `profile` / `search`），否则是**显式错误**。
- `default` 不是合法结果。解析不出原型 = 引擎错误（门禁失败），不是「普通页」。
- 判定只依赖业务结构（角色、`_lines`/`_items` 层级、`_rel`、关系、复合件），**不得**依赖站点名或「数价格/数菜单/数长段」这类偶然计数阈值。
- 长文/阅读型判定统计**全部长文本**（`_text`、`_quote`、嵌套 `_lines`），不得只看单一字段或固定段数阈值。

## 3. 布局框架（frames）是一等概念

页面原型映射到真实框架，而不是把一切倒进同一个文档列：

| 原型 | 框架 |
|---|---|
| marketing / landing | band 序列（满幅或色带）+ 居中/交替排版 |
| reading | 居中阅读列（单一 measure，hero 收敛到该列） |
| catalog / feed / search | 卡片网格 / 记录行网格；feed 用「主列 + 侧栏」两区 |
| detail | 媒体墙 + 主列 + 任务卡（右侧或栏内停靠） |
| profile | 居中身份卡 + 统计块 + 活动 feed |
| authentication | 居中表单卡 |

- **区域（region）**：主列与侧栏是两个区域，侧栏内容不得在单列流里掉到正文之后。
- 区域按声明角色取宽；页级框架决定对齐基线，局部表单不得各自选宽（沿用 `docs/m1/layout-axes.md` §5.2「容器按内容收缩」）。
- `[开放]` 「局部最优」布局研究（`docs/design-basis.md` §6）若落地，必须在构建期/缓存完成，运行期只套用方案。

## 4. 媒体角色（media roles）

- 图片按**声明的角色**定尺寸：hero/band 充满其框架；卡片缩略图充满其格子；正文插图受阅读列约束。
- 不得只按原图像素绘制（`width:auto`）而留下白洞或小图。
- 保持「绝不放大源图」判据（`docs/m1/layout-axes.md` §7.1）：按角色布局的是**容器**，图像在容器内等比、不放大。

## 5. 意图校验门禁：声明 → 兑现 → 大声失败

引擎必须把意图说成机器可读的声明（每页原型、每区框架、每媒体角色），渲染后校验计算样式是否兑现；不兑现即错误。三类检查：

1. **未定构图**：页面原型未解析或回落 `default` → 错误。
2. **死选择器**：结构选择器在冻结语料上 0 次命中 → 错误（写了不生效的 CSS 是缺陷，不是无害冗余）。
3. **级联覆盖**：某声明意图的实际计算样式与其声明不符（被更高/同权重后置规则、`!important` 或上限覆盖）→ 错误，并报出「声明值 / 实际值 / 获胜规则」。这就是自动化版的 DevTools 划线删除。

- 三者是**门禁（阻断）**，不是提示（audit）。
- **可证伪**：门禁必须先用已知缺陷做负样本证明能抓到，再谈通过（`docs/proof` 的 gate_probe 原则）。
- 权重口径：与既有「门禁全绿只是必要条件」一致；本门禁只证明「引擎兑现了自己的声明」，不证明设计好看——后者仍靠人审与独立复核（`docs/product.md` §2）。

## 6. 当前引擎缺陷（必须消灭，作为负样本）

- 页面原型靠作品数阈值推断，40 页中 32 页回落 `default`，无任何信号。
- 页种 CSS 大量「写了不生效」：`product-page` 0 命中、`catalog-page` 1、`marketing-page` 1。
- 阅读判定只数 `_text` 且跳过 `_quote`，长文被判成普通页。
- CSS 覆盖自身声明：`.gallery-mosaic{align-items:stretch}` 压掉 `aspect-ratio:1/1`；`.banner>.title{text-align:center}` 被同权重后置 `text-align:left` 覆盖；`.singleton-card>.stack{max-width:320px}` 把声明为 hero 的 banner 掐成 320px。
- 无「主列 + 侧栏」区域概念，侧栏在单列流里掉到正文之后。

## 7. 验收（10 页样板，铺开前）

- 10 个缺陷页作为样板：每页原型非 `default`、声明意图 100% 兑现、门禁负样本全部被抓。
- 交付形态：每页「原站 | 渲染」并排图 + 门禁报告。
- 样板通过后才铺到全部 40 页并重跑全部门禁 + 新独立验收。
